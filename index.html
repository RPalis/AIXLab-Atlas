This page is the map: what each stage is for, which skill you reach for inside it, and where the tools that don't belong to any one stage, or don't belong to the lifecycle at all, live.

Before Discover

Nothing exists yet

No README, no docs folder, not even a name for the thing. Two skills run before any of the four stages: one sets the table, the other gets the idea out of someone's head.

/setup

Bootstraps the repo's doc shell: README.md, a project AGENTS.md recording which skill owns which doc, and an empty docs/UNKNOWNS.md. Never touches application code.
/brief

Interrogates whoever already has the idea: product, audience, user types, core tasks, devices, competitors, constraints. Writes docs/PRODUCT_BRIEF.md, the domain brief persona expects as input.
01

Stage One

Discover

Understand the users and the problem before proposing anything. Everything downstream inherits what gets settled here.

/workshop

Two ways to run a workshop, from opposite sides of the same event.

  • planBuilds a design-thinking working session: activities selected by phase and timing, a written agenda, optional FigJam board or slide deck.
  • ingestTurns photos of the physical board that resulted into a deck, doc, CSV, or a replicated FigJam board.
/competitors

Who else is in this market, researched, not guessed at.

  • discoverSearches the web for candidate competitors, lets the stakeholder pick which to profile, then captures each one's features, workflow, and UX patterns.
  • addAppends one more competitor found later, without re-running the full scan.
  • analysisA deeper, evidence-rated pass organised by UX category, with a confidence tag on every claim and a ranked opportunity list.
  • benchmarkScores 3-5 products, yours plus competitors and best-in-class from any industry, 1-5 on one rubric with evidence, plus an adopt/adapt/avoid pattern library.
/interview

Research with real people, before, during, and after the sessions.

  • questionsPhase-aware kit: question bank, script, synthesis template. Discovery questions early, validation questions once something is built.
  • analysisTurns transcripts into evidence-backed themes, with every quote traced to its interview and weak signals flagged.
  • usabilityA bias-reviewed test plan and moderator script for a built prototype: task scenarios, success criteria, metrics sheet.
/persona

Formalizes user archetypes, mental models, and a chronological "Day in the Life" walkthrough that later skills read from directly.
/journey

Maps how a process actually runs today, not the proposed version.

  • mapCurrent-state process as a swimlane diagram: actors, steps, handoffs.
  • blueprintService-blueprint variant for a customer-facing process, with timing and cross-team wait times.
  • pain-pointsScores each step or wait time's friction, severity × frequency, with root cause.
  • solutionsFix directions and a measurable target per pain point.
  • experienceOne persona through one scenario: actions, thoughts, emotions, every claim cited or marked as an assumption.
/problems

Turns research into problem statements (never with a solution attached) and prioritised, traceable user stories. The last step of Discover.
/metrics

Defines OKRs against the framework that actually fits the product (HEART, CASTLE, or SELECT), each Key Result tagged by category.
02

Stage Two

Decide

Frame the problem, scope the objects, make the calls that get expensive to reverse once code exists.

/brainstorming

Turns one signed-off problem statement into many ideas, then a scored shortlist of directions. Never a single winner.
/map

Turns a prototype's structure — proposed or built — into something you can see instead of just read.

  • objectsInteractive OOUX/ORCA walkthrough (Objects, Relationships, Calls-to-Action, Attributes), seeding the object map and an entity-relationship diagram before any code exists.
  • iaOrganises content, navigation, labelling and search around the user's mental model. Every page and label traces to an input or is tagged as proposed.
  • sitePlans the proposed route/component architecture as a diagram, before any of it is built.
  • flowA complete, evidence-grounded end-to-end flow for one goal: every branch, error state, and exit, screen by screen.
/interrogate

Interrogates a hard call one question at a time until there's shared understanding, not a guess dressed up as a decision.

↻ also usable anytime
/decisions

Writes a decision up as a short, permanent ADR, including the alternative that seemed obvious and why it got rejected.

↻ also usable anytime
03

Stage Three

Design

Build the actual prototype. The largest stage: scaffolding, tokens, a find/fix craft loop, and the documentation that keeps the system legible as it grows.

/scaffold

React 19 + TypeScript + Vite + Tailwind v4 base scaffold, plus an optional site-type layer: dashboard, chatbot, marketing site, CRM, mobile app.
/styleguide

Establishes the two-layer token architecture (raw palette, then auto-flipping semantic roles) and generates DESIGN.md.

  • defaultStarts from a placeholder palette, for a new prototype with no real brand yet.
  • forgeCasts a real brand's colors, fonts, and spacing into the same architecture, from live CSS, a brand guide, or a verified hex matrix.
/audit

Finds problems, never fixes them.

  • craftScored UX critique — hierarchy, cognitive load, IA, consistency, responsive behavior, delight — feeds refine directly below.
  • heuristicDeep, evidence-based pass against 12 named usability heuristics, severity-rated 0-4.
  • codeCoding-standards check: token adherence, structure and reuse, mechanical hygiene.
  • specCompares the build to its approved design, screen by screen at every breakpoint, logging each drift with severity and owner.
  • a11yDeep WCAG 2.2 AA pass, criterion by criterion, with a mobile and screen-reader step. Run once the UI has stabilized.
  • perfMeasures load, interaction and layout-shift numbers on the built app against budgets, then lists the causes.
/refine

Fixes and unifies what audit's craft mode found: micro-interactions, responsive grids, dark-mode tuning, visual polish.
/storybook

Organizes the UI into the five Atomic Design tiers, builds Storybook stories, embeds the viewer in the prototype's own menu.
/map

Keeps every diagram honest once real code exists.

  • auditReconciles the object model against actual code alone, without a diagram refresh.
  • documentRegenerates the site diagram three ways (interactive modal, Mermaid, SVG) from the real built app, and reconciles the object model if it's drifted.
04

Stage Four

Deliver

Ship it, validate it, hand it off, and loop back to Discover for whatever the next round of real usage surfaces.

/audit

Coding-standards and design-fidelity audits, run before anything goes out the door.

  • codeToken adherence, structure and reuse, mechanical hygiene.
  • specBuild vs approved design spec, screen by screen.
/package

Three distinct handoffs, not one script trying to do all of them.

  • fullUnminified site + raw source + docs, a three-folder zip for a developer to read, extract, or rebuild.
  • liteMinified production/ folder only, bare essentials, for someone who just needs to run it.
  • figmaFlat, unminified files each under 1MB, to attach to a Figma Make chat.
/showcase

Packages work for people who weren't in the room: a presentation of the prototype, or a polished Word or PowerPoint version of any suite report.

  • storyDay-in-the-life PowerPoint deck from the prototype, with real screenshots.
  • revealA live reveal.js web deck.
  • docA Markdown report (an analysis, a benchmark, interview themes) converted faithfully into a styled Word document.
  • deckThe same report condensed into a PowerPoint, outline confirmed first, evidence tags and checklist kept.
/guide

Writes end-user documentation: a Getting Started section, then a phase-by-phase walkthrough of the real product.
/requirements

Reads the built prototype back into product language: Epics containing Features with user stories and acceptance criteria. Optional Jira/ADO export once an MCP server is connected.

How to actually use this

  1. 01Stages read top to bottom, but real projects don't. A mid-Design prototype can send you back to Discover after a workshop, mid-thought.
  2. 02Not sure where you are right now? Run /help (/ux-atlas:help with the plugin). It reads the repo's actual files and tells you the next move and the exact command to type, not the whole map.
  3. 03A multi-mode card means one skill, several jobs. Say the mode (/audit craft), or the skill will ask which you mean.

Usable Anytime

The tool belt

Not gated to a stage. Reach for these from anywhere in Discover through Deliver, whenever the situation actually calls for them.

/help

Where you are and what's out there, two ways.

  • defaultThe situational advisor: reads the repo's real state and recommends the next 1-3 skills, with the reason.
  • atlasThe full browsable index this page is drawn from: every skill, every phase, in one interactive reference.
/wiki

Compiles scattered notes into a small, interlinked markdown wiki as the project accumulates them, including a constellation graph view.

  • compileThe full pass: ingest every unprocessed source, answer a query, lint for contradictions, regenerate the graph.
  • noteLowest-ceremony capture: a quick thought dropped in and folded straight into the wiki, no separate compile step.
/figma

Moves work to and from Figma, whichever direction the moment calls for.

  • captureSends a live prototype screen into Figma as editable layers. No MCP needed.
  • importBrings a Figma frame or selection into the codebase as real, convention-conformant code.
  • syncBidirectional token sync between index.css/DESIGN.md and a Figma library's Variables.
/redline

Turns a specific, already-decided edit into real code — a marked-up screenshot, or pointing at a live element. No confirm step; the diff is the review.

  • markupReads circles, arrows, strikethroughs, and callouts on a screenshot — each annotation becomes one edit.
  • pickPoint at a live element in the running prototype and say what should change.
/moodboard

Maintains a persistent library of visual inspiration and synthesizes it into a living read of the direction — color, type, spacing, shape, elevation — each claim citing its source.
/restyle

Generates a few full-token-set candidate directions from references (or a moodboard), live-applied to the real running app so the choice is made against real screens, then hands the pick to styleguide.

Meta: Managing the Suite Itself

The one tool outside the map

Everything above moves a prototype forward. This one skill sits outside that lifecycle entirely: it manages the skill library itself, not a prototype.

/skill-manager

Manages the shared skill library at ~/.agents/skills, symlinked into Claude Code and Gemini CLI.

  • installClone or copy a skill into the library.
  • deletePermanently remove a skill.
  • disableMove a skill out of active use without deleting it.
  • enableRestore a disabled skill.
  • syncVerify and repair the Claude Code / Gemini CLI symlinks.
  • listShow active and disabled skills, each with its one-line description.
  • detailsShow full info on one skill: status, path, source, complete SKILL.md.
