# Audit: a11y mode

Part of the [`audit`](../SKILL.md) skill. Shared rules in `SKILL.md` still apply.

A full WCAG 2.2 **Level AA** pass (2.1 AA is a subset), organized by the four POUR principles. This is the deep audit; `code` mode keeps only cheap mechanical checks (focus-ring class present, Escape closes modals) as a fast hygiene pass, while this mode reasons about success criteria and produces a ranked, criterion-by-criterion report. Like `craft`/`heuristic`/`spec` modes, it only identifies issues; it doesn't fix them.

### Step 1: Perceivable

- **1.1.1 Non-text Content**: every `<img>` has meaningful `alt` (or `alt=""` if truly decorative); icon-only buttons have `aria-label`.
- **1.3.1 Info and Relationships**: heading hierarchy is a single `<h1>` per view with logical `<h2>`/`<h3>` nesting (no skipped levels); tables use `<th>`/`scope`; form inputs are programmatically associated with a `<label>`.
- **1.4.1 Use of Color**: color is never the *only* signal for status (pair a status badge's color with an icon or text, not color alone).
- **1.4.3 Contrast (Minimum)**: normal text ≥4.5:1, large text (≥18pt or ≥14pt bold) ≥3:1. Check every semantic token pair actually used (`text-primary` on `bg-surface`, `text-secondary` on `bg-page`, status text colors on their badge backgrounds) in both light and dark mode. A token pair that passes in light mode can fail in dark.
- **1.4.11 Non-text Contrast**: UI component boundaries (input borders, focus rings) and graphical objects ≥3:1 against adjacent color.
- **1.4.4 Resize Text and 1.4.10 Reflow**: text scales to 200% with no loss; content reflows at 320 CSS px width with no horizontal scroll. Sizes use `rem`, and the viewport meta does not block zoom.
- **1.4.12 Text Spacing**: raising line height to 1.5, paragraph spacing to 2x, letter spacing to 0.12em and word spacing to 0.16em causes no clipping or overlap.
- **1.3.4 Orientation**: the app works in portrait and landscape unless one is essential.

Run `node ../../../tools/check-token-contrast/check-token-contrast.mjs <src/index.css>` first. It computes every role pair in both themes. Cite its output instead of estimating ratios.

### Step 2: Operable

- **2.1.1 Keyboard**: every interactive element reachable and operable via keyboard alone; no click-only handlers on non-native elements without a matching `onKeyDown`.
- **2.1.2 No Keyboard Trap**: modals/dialogs release focus on `Escape` or close; nothing traps Tab focus permanently.
- **2.4.3 Focus Order**: tab order matches visual/reading order; no `tabIndex` values that jump illogically.
- **2.4.7 Focus Visible**: every focusable element shows a visible `:focus-visible` indicator; never `outline: none` without a replacement.
- **2.5.8 Target Size (Minimum), AA in WCAG 2.2**: pointer targets are at least 24×24 CSS px, or have 24px of spacing around them. (2.5.5 Target Size, 44×44px, is Level AAA. Use 44px as the practical bar for touch.)
- **2.4.11 Focus Not Obscured (Minimum), AA in WCAG 2.2**: a focused element is not fully hidden by a sticky header, footer or banner.
- **2.5.7 Dragging Movements, AA in WCAG 2.2**: every drag has a single-pointer alternative (a button, a menu).
- **2.3.3 and reduced motion (practice)**: animation that is not essential stops under `prefers-reduced-motion: reduce`. The token file must carry the rule, and any autoplay, parallax or loop must pause.
- **2.2.2 Pause, Stop, Hide**: anything that moves for more than 5 seconds has a pause control.

### Step 3: Understandable

- **3.2.1 On Focus / 3.2.2 On Input**: focusing or changing a field never triggers an unexpected context change (navigation, form submission) without warning.
- **3.3.1 Error Identification**: validation errors are identified in text, not color alone, and programmatically associated with their field (`aria-describedby`).
- **3.3.2 Labels or Instructions**: every input has a visible label or clear instructions; placeholder text alone is not a label.
- **3.3.7 Redundant Entry (A, WCAG 2.2)**: information the user already gave is not asked for again in the same flow.
- **3.3.8 Accessible Authentication (Minimum), AA in WCAG 2.2**: login does not depend on a cognitive test (remembering, transcribing). Allow paste and password managers.
- **3.2.6 Consistent Help (A, WCAG 2.2)**: help links sit in the same place on every page.

### Step 4: Robust

- **4.1.2 Name, Role, Value**: custom interactive components (not native `<button>`/`<input>`) expose the correct ARIA role, name, and state (`aria-expanded`, `aria-selected`, `aria-checked`) and keep it in sync with visual state.
- **4.1.3 Status Messages**: dynamic status updates (toast, inline validation, loading-to-loaded transitions) use `aria-live` so a screen reader announces them without requiring focus to move.

### Step 5: Mobile and assistive technology (when the prototype targets phones or tablets)

Reason about the screen with a screen reader even without a device: reading order, names, roles and live regions are visible in the markup.

- **VoiceOver (iOS) and TalkBack (Android)**: every control has a name and role; custom controls expose state; the swipe order matches reading order; decorative images are hidden (`alt=""` or `aria-hidden`).
- **Dynamic type**: layout holds at 200% text (see 1.4.4).
- **Touch**: targets meet 2.5.8; gestures have button alternatives (2.5.1 Pointer Gestures, 2.5.7).
- **Orientation and zoom**: no lock; the viewport meta allows scaling.
- **Motion and haptics**: no information is carried by motion or vibration alone.

```markdown
## Failing Criteria
For each failure:
- **[WCAG #] Criterion name** — Location: `Component.tsx`. What fails: [specific]. Fix: [concrete].

[What's genuinely solid — don't skip, it tells reviewers what not to re-check]
```

**Completion criterion:** every failure cites the specific WCAG success criterion number, not just a vague "accessibility issue," and names the exact component/file where it occurs.
