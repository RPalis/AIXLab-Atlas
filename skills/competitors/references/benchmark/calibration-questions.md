# Calibration questions

Two sets: the **input gate** (Phase 1 — ask before scoring) and **output calibration** (before you
build the deliverable). Never ask about anything already supplied. Cap
the opening gate at **five questions** and don't start until scope, products and rubric are clear.

## Input gate — the ≤5 that block scoring

Ask whichever of these are unresolved, in rough priority order:

1. **Evidence reach.** Hands-on walkthrough (is a browser tool available this run?), desk research
   only, or are you supplying screenshots / recordings? *This sets the confidence ceiling for the
   entire benchmark — ask it first.*
2. **Products (3–5).** Confirm the set, and label each: **yours**, **competitor**, or
   **best-in-class** reference. Which one is the product you're trying to move?
3. **Key tasks / flows (5–10).** Which tasks — onboarding, checkout, search, booking…? And are they
   **genuinely comparable** across every product? Flag any that aren't *before* scoring, not after.
4. **Persona + definition of "good".** Who is the user, and what does a "5" look like *for them*?
   Pull from a `persona` `card`-mode output if one exists. A nervous first-timer and a returning
   power user make opposite patterns correct.
5. **Rubric.** Default 10 dimensions (see `rubric.md`), or add / drop / reweight for this product?
   Is this a consumer product or a captive-audience / enterprise tool (→ add CASTLE)?

## Conditional follow-ups (only if relevant and unresolved)

- **Platform** — web, mobile app, or both? Patterns differ sharply by surface, and it changes what a
  walkthrough can reach.
- **Accessibility target** — a stated bar (e.g. WCAG 2.2 AA) sharpens dimension 9.
- **Existing design system / UX standards** — gives the "adopt/adapt/avoid" tags a home to point to.
- **Prior inputs** — is there a `competitors` `analysis` output, analytics, or prior research to feed
  in?
- **Product stage** — if pre-build, the "yours" column records the **decision required**, not a
  current capability. Say so, don't invent behaviour.
- **Weighting** — equal weights, or does the persona justify weighting some dimensions higher?

## Output calibration — before building the deliverable

- **Format** — the Markdown report plus a CSV scorecard, and whether a slide version is also wanted
  (see `deliverables.md`).
- **Scope of outputs** — all six deliverables, or a focused subset for this pass?
- **Averages** — raw per-product / per-dimension averages only, or weighted as well?
- **Audience** — who reads this, and what decision does it need to reach?
- **Cadence** — one-off, or the **first run of a recurring program**? If recurring, structure the
  `.md` so the same tasks and the same bar can be re-run next quarter.

## The rule underneath all of this

If a task is not comparable across products, **say so before scoring** — a benchmark built on
non-comparable tasks produces confident nonsense. When in doubt, ask rather than assume.
